## 1. P1：无关存储事件清空正在填写的关联解释

位置：`app/data/research-history.tsx:39–41`、关联组件挂载位置及 `app/data/analysis-project-link.tsx:12`。

在已保存分析快照的“关联快照到项目”中输入解释，触发一个其他项目草稿键的 storage 事件。history 的监听不筛选键，先 setOwner(null)/setItems([])，使关联组件卸载；重新加载后输入变成空字符串。新 A 批会在每次项目笔记输入时写 localStorage，因此两个工作标签页同时使用会自然触发此情形。

浏览器已复现。虽然宽泛监听原已存在，新引入的关联表单让它成为丢输入的实际路径。修复应筛选账户/历史键，并避免正常刷新先清空有效快照；解释与下一步任务草稿不能因无关事件消失。

证据：[cross-tab.json](../../outputs/revision-review-2026-10-23/cross-tab.json)。

## 2. P1：新断词修复在每个段落重复扫描整篇论文

位置：`app/papers/page.tsx:1171` 调用 `app/papers/pdf-text.ts:130–132`。

每次 flush 都将整篇 evidenceText 传入 joinPdfLines，后者反复 lowerCase、正则分词和构建两个 Set，即使当前段落没有断词也执行。设全文字符量 N、段数 P，相关工作量约为 O(N×P)，随文档规模接近平方增长；第二阶段在客户端同步循环执行。

只读 Node 合成复现：84,000 字符/100 次 flush 约 176.9ms；420,000 字符/500 次 flush 约 6496.7ms。此为指定文本处理函数成本，不是实际 PDF 导入总耗时，也不是线上 INP；但足以确认新增的重复工作与长任务风险。此前数据页的优化数字不能覆盖导入链路。

修复应每篇只构造一次共享词表/复合词索引，并对不含断词候选的段落跳过相关判断，再检查代表性长 PDF。

证据：[parser-cost.json](../../outputs/revision-review-2026-10-23/parser-cost.json)。

## 3. P2：历史损坏时，备份恢复入口一起失效

位置：`app/data/research-history.tsx:39,67`。

本机历史 JSON 损坏或校验失败时，load 在设置 owner 前抛错；owner 保持 null，而新“从 JSON 恢复快照”输入以 !history.owner 禁用。用户已经登录，也有合法备份，却无法通过所提供的入口恢复。只验证“删除后导入”不足以证明损坏恢复闭环。

浏览器以隔离账户的损坏历史复现。应分离账户身份确认与内容解析失败；保留损坏原件并提供安全恢复到新集合/明确替换的入口，不能要求用户自行清空整站存储。

证据：[recovery.json](../../outputs/revision-review-2026-10-23/recovery.json)、[界面](../../outputs/revision-review-2026-10-23/recovery-blocked.png)。

## 4. P2：课程列表续学忽略较新的待同步本机位置

位置：`app/courses/course-resume.tsx:28`。

同一 generation，本机在离线/上传失败后已有 lesson-2，服务器仍是 lesson-1。目录直接调用 mergeCourseSnapshot；该函数保留远端 lastLessonId，只合并完成和练习记录。目录不读取已有待同步队列，于是继续入口回到旧课时，并将 local/error 都标为 false。

只读调用当前合并函数已复现 lesson-2 + lesson-1 → lesson-1；未在真实账户造离线记录。应结合已有队列顺序识别更新的本机位置并显示待同步状态，同时维持目录只读、不写完成进度的约束。

证据：[course-position.json](../../outputs/revision-review-2026-10-23/course-position.json)。
